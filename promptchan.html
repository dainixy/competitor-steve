API · Chat endpointstateless chat = no server-side memoryshallow personality
★ Chat API — POST /api/external/chat. Confirms what we suspected: the chat layer is stateless on the server. There is no persistent memory. The caller must pass chatHistory[] on every request. Promptchan's frontend almost certainly stores chat history client-side (localStorage / IndexedDB) and re-uploads the whole transcript every turn. This explains:
  • Why their chat "resets between sessions" — there's no server-side store for it. Clearing localStorage = clearing memory.
  • Why chat is cheap to operate — no DB writes per message, just stateless LLM inference. Massive cost advantage vs Nomi's persistent memory architecture.
  • Why "Create Image from Scene" works inline — see selfie field in the response below. The chat endpoint can synchronously generate and return an image when the context warrants it.
Request shape: { message, characterData, chatHistory[], isRoleplay, redo, userName }. The characterData object is the personality config: 
{
  name: string,
  personality: string,    // one description blob
  scenario: string,       // setting/context
  sexuality: string,
  openness: 0|1|2,        // 3-value integer slider
  emotions: 0|1|2,        // 3-value integer slider
  age: int,
  gender: string
}
Two 0-2 integer sliders for personality depth. Compare to Nomi (Backstory, Desires, Boundaries, Preferences — all free-text, multi-paragraph, plus Mind Map graph + Identity Core + Shared Notes) or Kindroid (5-tier cascaded memory + voice/LLM picker + dynamism slider). Promptchan's personality model is ~50× shallower. This is the technical proof of our earlier read: chat is bolted onto an image-gen product, not a companion product.

Response: { audio (string|null), chatHistory[], message, selfie (string|null) }. So a single chat call can return: text reply + TTS audio + an inline generated image (the "Create Image from Scene" feature). All three modalities in one round trip. This is actually elegant API design — for the image-gen-first product they're building.

For DRT.FM (companion-first):
  • Don't copy this architecture. Server-side memory is the moat we're competing on; can't ship it as stateless.
  • Do copy the multi-modal response. Returning text + audio + optional inline media in one call is much nicer than three sequential round-trips. We should consider this for DRT.FM's chat API.
  • Personality config needs depth. Free-text fields for backstory/desires/boundaries beats 0-2 integer sliders by 10× on engagement.
  • "redo: true" flag — Promptchan lets the caller request a regen of the last reply without re-sending the full transcript. Worth copying for our chat UX.

Submit params: aspect (Portrait/Landscape/Square) · audioEnabled (bool) · prompt (required) · style (10 models: Real, Photo XL+, Photo XL+ v2, Hyperreal XL+, Hyperreal XL+ v2, Cinematic XL, Anime XL, Anime XL+, Render XL+, Illustration XL+) · sliders (age ≥18, weight/breast/ass -1..1) · seed · pose (same 200-pose library as image API). Standout patterns for DRT.FM:
  • Public queue depth on long-running ops. Showing "you're #47 in a queue of 230" beats Kindroid-style "generating..." opacity. Users tolerate waits when they can see why.
  • initial_queue_length + current_queue_length together = clients can compute "you've moved up X positions" without server-side tracking. Smart minimal-state design.
  • Signed temp-URL delivery — videos return as ephemeral GCS URLs (one-time download links). Reduces storage cost (clients download once, cache locally) and avoids hot-linking. Use for DRT.FM's video output.
Avoid:
  • No webhook callback for async video. Polling only. Wastes client/server cycles. We should support webhooks from day one for video.
  • No documented rate limits or timeouts. Caller doesn't know how long to poll or how often. We document these.
