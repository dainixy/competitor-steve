Competitive Recon System

An internal pipeline that captures competitors' engineering artifacts — UI code, API specs, AI prompts — instead of typing notes about them.

1.Problem Statement

Dainis (founder/PM at DRT) needs deep competitive reconnaissance on 5 paid AI-companion competitors (Candy.AI, OurDream.AI, SecretDesires.AI, and 2 others). The current plan is fully manual: open each site, take screenshots by hand, type qualitative notes, move on. Budget: 1-2 hours per site = 5-10 hours of repetitive work, repeated whenever a competitor ships.

The deeper problem isn't time — it's artifact quality. Manual screenshots and prose notes give Steve descriptions ("they have a chat layout with images inline"). What Steve actually needs to build features is the engineering substrate: the API contracts, the actual frontend code, and the competitor's literal LLM prompts. None of those are produced by manual recon.

A secondary problem: many cloud AI tools refuse to operate on adult content sites, and uploading credentials/screenshots from paid accounts to third-party clouds is a privacy and TOS risk.

2.Solution

A locally-run, three-pass recon pipeline that Steve sets up once and Dainis reuses indefinitely.

  • Pass 1 — Passive Capture: Dainis triggers a recon run on a competitor. The system launches mitmproxy, a dedicated browser profile, OBS screen recording, and a Browser Use autonomous agent. Dainis can run alongside for qualitative voice notes.
  • Pass 2 — AI Extraction: The system converts raw captures into structured artifacts: OpenAPI 3.0 spec, intercepted LLM prompts, cloned React components, vision-model quality ratings, and a feature inventory.
  • Pass 3 — Delta Automation: A scheduled Stagehand script re-runs the recon weekly and produces a diff report ("OurDream added 2 endpoints + a voice settings screen since last Monday").

Everything runs locally. No cloud uploads. No content filters. Output bundle per competitor is a clean folder Dainis can hand to Steve.

5.Implementation Decisions

Modules (tiered by phase)

Seven modules across three phases. Build v1 first (4 modules), run it once, then decide on v1.5.

  • v1 MUST = ship in first release, ~1.5-2.5 weeks of Steve time
  • v1.5 SHOULD = adds ~4-7 days after v1 proves itself
  • v2 LATER = only valuable once baseline runs exist
  • DEEP = simple in/out interface, prioritised for isolated tests
1. Capture Orchestrator v1 MUST shallow
In: competitor config (name, URL, profile, mission). Out: a populated ./recon/{competitor}/raw/ folder with mitmproxy flows, OBS video, screenshots, Browser Use logs.

Wraps four external processes (mitmproxy, OBS, browser, Browser Use agent). Shallow because most of its body is process management and config.

2. Network Capture Exporter v1 MUST DEEP
In: mitmproxy flows file. Out: api.yaml (OpenAPI 3.0), llm-prompts.json (intercepted system prompts + model params), raw.har.

Pure transformation. Internally uses mitmproxy2swagger plus a custom extractor that scans for known LLM provider endpoints (api.openai.com, api.anthropic.com, etc.) and pulls request bodies. Easy to test with fixture flow files.

3. Browser-Use Mission Runner v1 MUST shallow
In: mission prompt (e.g. "explore all 30 features"), browser profile path, target URL. Out: screenshots/, features.json, mission-log.txt.

Thin wrapper over the Browser Use library + local Ollama. Includes retry/checkpoint logic so long missions can resume. Not deep-tested — stochastic external dependency, validated via dry runs instead.

4. UI Cloner v1.5 SHOULD shallow
In: list of URLs + optional screenshot paths. Out: components/{name}.tsx files.

Wraps Open-Lovable / v0 / Magic Patterns APIs. Bonus path: if source maps detected on the target, runs unwebpack-sourcemap and dumps the recovered React tree.

5. Vision Rater v1.5 SHOULD DEEP
In: screenshot folder + rubric (list of dimensions like "voice realism 1-10", "image quality 1-10"). Out: ratings.json with per-screenshot scores + overall aggregates.

Wraps Qwen2-VL via Ollama with a structured-output prompt. Pure transformation given a fixed model + rubric. Easy to test with golden screenshots and tolerance windows.

6. Delta Engine v2 LATER shallow
In: two recon-run output folders for the same competitor. Out: diff.md highlighting new/removed endpoints, new screens, prompt changes, rating shifts.

Mostly diffing structured JSON. Deepish, but only one real consumer (the weekly cron), so kept simple.

7. Report Bundler v1 MUST shallow
In: the full ./recon/{competitor}/ folder. Out: an HTML index + a zipped bundle for handoff to Steve.

Templating + file collection. Trivial; mentioned for completeness.

Architectural decisions

  • Everything local. No data leaves the machine unless Dainis explicitly opts into v0/Open-Lovable cloud APIs for a specific clone step. Default: fully air-gapped.
  • One Chrome profile per competitor. Profiles live in ./profiles/{competitor}/. Cookies, mitmproxy CA cert, and login state isolated.
  • Filesystem as the database. All artifacts are files on disk in a predictable structure. No database. Steve can grep, diff, version-control them directly.
  • Local LLM by default. Browser Use and Vision Rater both target Ollama locally. API keys (Gemini, Anthropic) are opt-in fallbacks for specific tasks.
  • Failures are first-class output. When the agent hits a CAPTCHA, login wall, or refusal, it logs a structured blockers.json entry rather than crashing.

6.Testing Decisions

Principle: test only external behavior of each module — given input X, does it produce output Y? Don't test internal helpers. Don't mock external services; use fixtures instead.

Tested modules (both deep):

  • Network Capture Exporter — fixture: a small captured flows.mitm from a safe target (e.g. a public weather API + a known LLM call). Assertion: produced api.yaml matches a golden file; llm-prompts.json contains the expected system prompt.
  • Vision Rater — fixture: 5 screenshots with known ground-truth ratings. Assertion: model output is within ±1 of ground truth on each dimension. Tolerance window because the model is non-deterministic.

Untested modules (validated by dry runs, not unit tests):

  • Capture Orchestrator — too many external processes; smoke-tested via the "test on safe target" mode.
  • Browser-Use Mission Runner — stochastic LLM-driven agent. Test by running on a known SaaS target and checking the output folder is non-empty + features.json has expected shape.
  • UI Cloner — wraps external APIs; testing would just test their stubs.
  • Delta Engine, Report Bundler — small, transparent, low-risk.

Prior art: none — this is a greenfield project. Steve sets conventions.

7.Out of Scope

  • CAPTCHA / anti-bot bypass — when the agent hits one, log it as a blocker and skip. Dainis handles manually.
  • Mobile app recon — web only for v1. (Cert pinning makes mobile mitmproxy painful.)
  • Sites with HTTP cert pinning — rare on web, but if hit, log as a blocker.
  • Real-time alerting — weekly cron only. No Slack/email push for v1.
  • Multi-user / team collaboration — single-machine, single-operator (Dainis).
  • Paid subscription auto-purchase — Dainis subscribes manually; the system uses his logged-in session.
  • Custom dashboards / pretty UIs — the output is files in folders. If Dainis wants a dashboard later, that's a follow-up project.
  • Re-implementing competitor features — this system captures intel. Building DRT's competing features is Steve's separate work using the artifacts.

8.Further Notes

  • Browser Use success rate caveat: the 89.1% benchmark is on general web. AI-companion sites have heavy custom JS, modal flows, and dynamic chat UIs — expect closer to 60-70% one-shot success. Plan for 1-2 reruns per site.
  • System prompt extraction depends on architecture. If a competitor proxies LLM calls through their own backend (most do), mitmproxy catches them. If they call LLM providers client-side, it still catches them. The only miss is if they use an on-prem LLM with no external API call — unlikely at this market stage.
  • Source maps are a coin flip. Some competitors leak them, some don't. Detect-and-extract is a bonus path, not a guaranteed deliverable.
  • Cost ceiling: entirely local stack is $0/run. Adding Gemini API for vision ratings tops out around $10-30 for a full 5-site sweep. Adding v0 / Open-Lovable Pro is ~$20/mo flat.
  • Legal note (not a blocker, just awareness): reverse-engineering for competitive analysis is a normal industry practice, but Dainis should not publish extracted system prompts or cloned components verbatim. Use them as engineering reference, not as shipped code.
