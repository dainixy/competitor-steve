## 07. Prototyping

The PDF gives you the "why prototype" rules. The video is a full tool walkthrough (Figma native prototyping, then Principle) with specific techniques not in any deck.

### Figma native prototyping — what it's actually good for
- Workflow: select an element → Prototype tab → drag the connector from element to target frame. Interaction triggers available: on click, on drag, while hovering, while pressing, mouse enter. Transition types: instant, dissolve, smart animate, move in/out.
- **Rule of thumb on transition type**: for testing web flows, use **instant** — matches the real end experience (a live webpage doesn't dissolve between pages). Save fancier transitions (dissolve, move) for app prototypes where that's the native feel.
- "Fixed position when scrolling" checkbox = instant sticky-nav/sticky-sidebar test. Click it, hit Present, scroll — done in "a couple of clicks." Good enough to validate the interaction with real users before it's built.
- **Known Figma limitation** (explicitly named): Figma can't recognize "extended scroll area" and stop scrolling at a natural boundary — it just keeps scrolling forever. For that class of interaction (and anything with scroll-triggered timing), you need Principle.
- Native prototyping in any tool (Figma/Sketch/XD) is explicitly framed as sufficient for **linking pages and simple flows**; reach for a dedicated prototyping tool only when the interaction itself needs to be designed (timing, easing, scroll-driven state changes).

### Principle — import & component workflow
- Import assets from Figma: File → Import from Figma → pick the frame → set **2x scale for mobile/retina work, 1x otherwise** (concrete number given on the record).
- Building a hover-zoom component: duplicate the artboard for the "hover inside" state, then **select the inner image, not the outer frame**, before scaling — scaling the frame instead of the image is called out as the easy mistake to make.
- Interaction settings: separate "hover inside" and "hover outside" states (in vs. out is not automatic/symmetric — you set both).
- Animation controls: duration is adjustable per-interaction (demo values: **1 second vs. 0.3 seconds**); easing options are **Default, Easy, Ease In, Ease Out, Ease Both, Spring, Linear** — pick per interaction, no single default recommended beyond "try it and look."
- Components nest: an animation defined inside a child component still fires correctly when that component sits inside a parent flow — build small interactive pieces once, reuse them across bigger prototypes.
- For embedded video assets: don't add a hover interaction — "let the animation play" on its own. Treated as a deliberate exception to the hover pattern used on static images.
- Explicit process note: *"Design and prototyping is all about trial and error and sort of getting things to feel exactly as you'd like them to be."* — tune scale/timing by eye, iterate, don't lock the first value.

### Drivers (scroll-linked property changes) — the core Principle technique
- To make anything scroll-reactive: select the scrollable panel → set interaction to **Scroll** → the Drivers panel populates keyed to the Y position.
- Principle won't scroll if there's nothing below the frame — you must **manually extend the canvas** with dummy content, or (the actual trick used) add a plain rectangle below the content, set its **opacity to 0**, and nest it inside the scrollable layer. It creates scroll "room" without being visible.
- Sequencing rule for cross-fades: when one element should fade out before the next fades in, don't just set both to trigger at the same driver keyframe — **drag one keyframe's position earlier on the timeline** so the first element is fully gone before the next appears. Demoed catching and fixing exactly this overlap bug live.
- To keep a persistent UI element (e.g. pagination dots) from being dragged along by a scroll-position driver, **pull it outside the driven panel/group** entirely — it's not a driver setting, it's a layer-hierarchy fix.
- Drivers can control **multiple properties concurrently** on one keyframe — e.g. animate opacity AND center-Y position together so an element fades while it also slides, or so one nav fades out at the same time a second nav slides in. Select both properties, add both to the same driver keyframe.
- Full worked example (sticky nav morph): as user scrolls, (1) old top-nav text group's opacity → 0 and Y-position slides up together, (2) new header nav is imported fresh from Figma (File → Import from Figma → Import Selected Frames), pasted at opacity 0 above the frame, then its opacity → 100 and Y-position slides down, timed to land as the old nav finishes fading. Net effect: one nav visually morphs into another purely via driver keyframes on two overlapping elements, not a single animated object.

### Specific micro-interaction recipes demoed
- **Modal close "X" button**: build as hidden by default, rotated **62 degrees**; on the triggering frame it becomes visible and rotates to 0 degrees. That rotation-in is the entire effect.
- **Mobile swipeable pagination**: use Principle's native **"Page Horizontal"** element — it auto-snaps drag distance to the width of the next block, so you don't hand-animate each swipe. Pagination dots are highlighted via drivers keyed to the same drag position (opacity swap per dot as you cross each threshold).
- **Sticky add-to-cart drawer (mobile)**: nest the "Checkout" text/button below the visible button; on trigger, the drawer scales/extends open and the nested text slides up into view while opacity → 100%. Reuse the same nested-reveal technique both directions (open/close).

### Testing & delivery practices
- Test every prototype **on the actual target device**, not just on a laptop screen: install the Principle mobile app, mirror the file, and manually check — "Is the timing correct? Does everything feel within reach? Is it highly intuitive?" These three questions are the stated bar for pass/fail.
- Principle can **export the interaction as a screen-recorded video** with a selectable cursor style (touch / arrow / none — none shows a big circle at touch points). Use this for portfolio pieces or remote client review when you can't hand someone the live file.
- Placing a device mockup (phone frame) around the prototype before presenting to a client is called out explicitly as a presentation aid — it helps a non-technical stakeholder imagine the interface on real hardware rather than on a laptop screen.
- Tool-selection rule for complex logic: if the prototype needs conditional logic (form validation, if/then branches, special states), don't force it into Principle — use **Axure, UXPin, Framer, or vanilla code** instead. Principle/Figma are for feel and flow, not logic.

## 08. Putting It All Together — Part 1 (Design Vision Document)

The PDF only says "design systems exist." This video shows the actual **document that precedes the design system** — a "design guide and vision document" — with real Vespy content, template-style, worth lifting wholesale as a checklist.

- Concrete process discipline: before opening any design tool, spend roughly **one hour** re-reading every prior discovery artifact (briefs, personas, IA) "to really synthesize all of this information and get it fresh in my mind... so I can design with objectives and a clarity of thought." Named as a deliberate step, not busywork.
- The design vision doc's actual sections, in order, with the real numbers used as an example (use these as a fill-in-the-blank template):
  1. **North Star statement(s)** — one or two lines the whole project is judged against (e.g. "deliver a personalized and simple online shopping experience that captures the heart and soul of our stores").
  2. **What we know** — hard business/analytics stats that should shape decisions. Example numbers given: **70% of purchases originate from social + email traffic**; **1 in 8 customers are repeat customers**. Framed as "bring in business stats that can help guide our decisions" and are useful to show non-design stakeholders too.
  3. **Business objectives for the quarter**, stated as numbers: *increase conversion to sales by 15%, increase traffic through search/social, launch the new design system from the ground up, grow social + email lists by 10%.* The instruction: define these BEFORE designing so you "know what we're working towards."
  4. **Customer personas** — deliberately kept light: *"these don't have to be that detailed, it's really just to have a face to the type of customer we're servicing."* Each persona gets a name, a role label (visitor / fan / explorer / hunter), and primary device (mobile vs. laptop) — that's it at this stage.
  5. **User epics** — one-line primary objective per persona (e.g. explorer wants inspiration; hunter wants "a formal but casual watch between $500–$1,000").
  6. **User goals/outcomes as direct quotes** pulled from actual research interviews/surveys — verbatim language, not paraphrased, "to get into the mind of the user in their own words."
  7. **Target emotional arc, mapped to funnel stage**: during discovery/browsing, the target feeling is *informed* (explicitly NOT "inspired" at that stage); post-purchase, the target feeling is *satisfied and happy*.
  8. **A maturity pyramid you climb over the project's life**: functional → reliable → usable → **pleasurable**. Explicit sequencing rule: *"when we're first building, all we want the site to be is functional... we build and market test from here [before] eventually we want to move up this pyramid."* Don't try to ship "delightful" on day one; earn it in that order.
  9. **Design principles as principle+action pairs**, not just adjectives — e.g. principle "personable and human" pairs with the action "use language from the street, not from a corporate giant... allow personalized support from a real person," with the stated result "make the brand feel relatable... bring the great local-store offline experience online." This action-clause format (principle → concrete behavior → intended result) is the reusable template.
- Closing framing: this document is explicitly called *"the beginnings of our design system"* and is described as valuable specifically "when you're working and leading a team" — it's a team-alignment artifact, not solo scratch notes.

## 08.1 Putting It All Together — Part 2 (live build walkthrough)

This is a full screen-recorded build from blank canvas to a finished Vespy homepage. Most value is in the *sequence and habits*, not any single fact.

- **Canvas prep ritual** (do this before any design work): paste, loosely and messily, around the edges of the main artboard — the styleboard, key screens from the design-vision doc (goals + principles), the sitemap (copied from Whimsical via its share → "copy image" export), the approved wireframes, and the personas. Explicit reasoning: *"the key is not to be pretty or perfect... every time we're designing we're looking if we're hitting these goals, if we're meeting these objectives."* It's a working reference wall, not a deliverable.
- **Which page to start with** — stated rule, not just habit: start with *"the page that will dictate the direction for everything else."* Concretely: dashboard first for a complex web app; home/landing page first for marketing or e-commerce sites; the single most-used screen first for a mobile app.
- **Canvas sizing decision**: chose a large **1920px** canvas deliberately to design for the largest screens first, cross-checked against analytics (majority screen size) and against which personas are mobile-only vs. desktop. Mobile and desktop are worked "concurrently," tablet is deliberately done last unless tablet is the primary platform.
- **Storytelling-first reasoning, explicitly contrasted with ego-driven design**: *"What I'm designing, I'm always thinking with the mindset of the user rather than — okay, this would look cool, this would win me an award. Really, what can I do to serve the user?"* Before any high-fidelity work, ask what a specific persona's first impression should be.
- **Concrete homepage narrative order used** (his actual answer to "what does the user need to see, in what order"): aspirational hero imagery + succinct brand copy → "more than just a store" culture/mission content → social proof (press quotes) → social media presence → email capture → footer. Self-aware caveat: *"this is a pretty common layout for a lot of e-commerce sites, I'm not reinventing the wheel here."* Lesson: default to the proven pattern unless you have a specific reason to deviate.
- **Block-first layout method**: rough out layout as flat colored rectangles/regions with NO content or labels first, to lock macro structure (e.g., decided on a split-screen: nav bar + roughly half-screen hero) before touching type or imagery. Only labels sections afterward, and says explicitly he skips labeling in his own real work — he's only doing it on camera to narrate his thinking.
- **Build multiple layout variations before committing** — after the first block pass, explicitly drags the canvas out and builds a second full alternative (e.g., full-bleed banner/lookbook-style hero vs. the split layout) rather than refining the first idea in place.
- **Typography enters only after macro layout is settled**: pulls real typefaces from the styleboard (**New York + Lato** in this project), sets navigation type, then uses Figma's "distribute horizontal spacing" to evenly space nav items rather than eyeballing gaps.
- **Baseline number given on the record: the baseline unit is 12px**, and type/spacing choices are kept to "multiples of 3 or 4" of that unit to stay consistent — this is the first place in the whole course a literal grid unit number is stated.
- **Heading discipline rule, stated directly**: *"h1 should only occur once on a page."* If a piece of text is visually too big for its importance (his live example: "Latest Happenings" felt oversized as an h1), demote it to h2/h3 rather than force it — heading level should track information hierarchy, not just "biggest thing I want to be big."
- **Componentize the moment something repeats**, not later in a dedicated "systems" phase: as soon as a type style or logo has been placed more than once, immediately turn it into a Figma style/component and file it into a running "assets"/library page. Naming convention used live: name components exactly what they are (h1, navigation, paragraph, etc.) so search later actually works.
- **Payoff demonstrated concretely**: once nav text is a shared style, a single global edit (e.g., switching nav text to uppercase) propagates everywhere at once — explicitly contrasted with the alternative of manually updating **"30 to 100 screens"** individually. This is presented as the entire business case for componentizing early rather than at the end.
- **Mobile pass discipline**: switch to a phone frame once desktop "feels" right, but don't try to resolve every mobile detail immediately — *"we don't have to solve everything here at once... it's just all about play at this point and using your eye to adjust."* Uses **Figma Mirror** on a real phone specifically to judge type size and image height "in the hand" (ergonomics), not just on a scaled-down monitor view.
- **Share-early rule, stated as a warning against a specific failure mode**: *"don't try to polish everything for like weeks or months, that's a really a waste of time."* Get a Figma Present-mode link in front of stakeholders/team the moment there's a rough version, and iterate from their reaction rather than solo-polishing.
- **Image sourcing order**: client-supplied assets first; Unsplash (or similar stock) second, used both as a temporary placeholder AND as art direction for what should eventually be shot for real.
- **Cross-pollinate prototyping mid-build, not after**: while the homepage was still a static Figma comp, jumped into Principle to test a scroll-triggered nav-morph idea (the same technique detailed in the 07 Prototyping video), then folded the validated idea back into the static Figma file. Explicit instruction: *"even if it's not finished yet, don't be afraid to start prototyping — that's the perfect time."*
- **Personalization example tied back to brand voice**: for a logged-in returning user, homepage swaps in a different module — a discount callout copy-written in brand voice ("Hey, thanks for being part of the fam, get 50% off your next item — yep, not a typo") — shown as evidence of feeding the design-vision principles ("personable and human," "casually sophisticated") into actual UI copy, not just layout.

## 08.2 Putting It All Together — Part 3 (scaling to the rest of the site)

- **Page-status kanban directly on the canvas**: color-code page frames — green = approved/final, another color (blue) = in progress, blank/uncolored = not started. Simple, low-tech tracking method for a growing site map, usable solo or with a team.
- **Page taxonomy to plan for, before building**: category pages (men's/women's), product-detail pages, top-level content pages (journal, about), article/content pages, tag-filtered pages, and *system* page sets that need their own template families — checkout flow, error handling, password reset, email sequences — plus UI-state overlays like the cart modal and search field. Naming and bucketing this list up front is presented as the actual "putting it together" step, done before any pixel work on the remaining pages.
- **Practical plugin tip**: Figma's native mask only respects the top layer of a selection (unlike Photoshop-style masking) — use the **"Easy Mask" plugin** instead if you're used to Adobe's masking model. Called out as a genuine gotcha for anyone coming from Photoshop/Illustrator.
- **"Don't reinvent the wheel" reuse method, made concrete**: for a category/listing page, don't design from a blank page — reference sites you've personally used and found intuitive, plus award/inspiration sites (Site Inspire named), bring the pattern back, and improve it. Explicit permission to copy proven structure and differentiate on execution, not invent new IA for its own sake.
- **A/B mindset applied to layout exploration, not just to running tests**: for the category page, built at least two real alternatives (split-screen vs. full-bleed image hero) before picking a winner "part intuition, part data and feedback." Explicitly keeps the rejected variant **"in your back pocket"** for a future split test rather than deleting it.
- **Concrete drop-shadow spec for a UI element**, given on the record: cart dropdown modal uses **250px blur at 20% opacity**. Arrived at by testing alternatives live — no shadow (blended into page, rejected), a plain grey stroke (better but still not enough separation), then the wide/soft shadow (chosen). Worth keeping as a literal starting value for "modal needs to visually separate from page" — soft and wide beats a hard, tight shadow.
- **Auto Layout used for resilience, not just spacing**: cart modal built with nested Auto Layout groups specifically so the panel *reflows automatically* as items are added/removed. Explicitly stress-tested by pasting ~30 duplicate line items to see whether the panel handles the edge case gracefully — treated as a required design step, not optional QA.
- **Stakeholder-defense habit**: ties every layout decision on the category page back to the two-line brand principles from the vision doc — *"I've really done nothing more than that — just showcase the images, the brands, and let that do all the talking."* The instructed technique: when presenting to stakeholders, always have a principle-based reason ready for *why* a screen looks restrained/sparse, don't just say "it looks better."
- **Responsive cascade pattern given as a named sequence**: for a grid of cards/features, the concrete breakpoint behavior demoed is **3-column → 2-column → 1-column ("block of 3, then block of 2, then a block of 1")** as screen width shrinks — stated as "a common pattern you can use when working with each screen size," i.e., a reusable default for card grids specifically.
- **Explicit anti-device-catalog philosophy on breakpoints**: *"just because the iPad or iPhone is a particular size... even the sizes in between should work nicely... the design should just break whenever it's naturally occurring — that could be 1400, could be 1200, could be any size."* Don't design to named devices; design so the layout organically breaks wherever content demands it.
- **Icon/type stroke-weight pairing rule**, demonstrated live: match an icon's visual stroke weight to the adjacent letterform's stroke weight — *"if that was way too thick it would look weird... if that was way too thin it would look weird... the thickness is just right based on these letterforms."* A concrete craft check most designers skip.
- **Worked hierarchy example on an article page** (a literal size-ladder you can copy): pull-quote (largest/heaviest) → subtitle (next size down) → comments (smaller than subtitle) → "Related Stories" heading (jumps back up — new content block) → related-story items (smaller again). Shown as proof that font-size choices should map directly to reading priority, block by block, not be uniform.
- **Finishing-pass habit**: run a Figma spell-checker plugin over all copy as a required last step before calling a page done (a live typo — "Jun" for "June" — was caught and fixed on camera specifically to make this point).
- **Checkout-page UX rule, stated as a warning against a known dark pattern**: strip the nav and footer on checkout entirely to remove distraction and focus, but explicitly **keep a working way to exit/go back** — calling out that some sites disable back-navigation once you're "locked in" to checkout and naming that a **dark pattern** to avoid.
- **Reference the platform devs will actually build on**: checkout form fields and flow were explicitly modeled on Shopify's existing components (breadcrumb, pagination, input fields) rather than invented fresh — reasoning given: agree the underlying platform/tech with dev + client first, then reuse its existing patterns and re-skin them in brand language instead of reinventing form UX.
- **PayPal-logo case study (aesthetics vs. recognizability trade-off)** — the most concrete "judgment call" example in the whole module: a black/elegant PayPal mark matches the Vespy aesthetic better, but the standard blue-and-white PayPal logo is what users actually recognize as "the PayPal button" at a glance. Stated resolution: default to the recognizable version unless a split test proves otherwise; explicit warning against both failure modes — *"don't get fooled by just purely numbers"* (over-indexing on conversion data into ugly, incoherent UI) and, implication throughout, don't over-index on pure aesthetics either. Use judgment, validate with data when you can get it.
- **Full post-purchase lifecycle treated as in-scope design work, not an afterthought**: order-confirmation email → shipping/tracking email → delivery/thank-you + feedback request → loyalty/discount email. Explicit analogy: Apple's unboxing experience as the standard for treating the entire post-checkout journey — not just the last screen in Figma — as part of "the designed experience." Competitors (Samsung named) are cited as having started catching up on packaging specifically because of this bar.
- **File-hygiene / team handoff convention**: keep one canonical **"master"** file/page that only receives merged, *approved* work; all in-progress design and prototyping happens in duplicated copies, merged back only after approval. Stated as the job of whoever leads the project (principal designer/creative director) to gatekeep.
- **Top-level layer-naming convention**, given explicitly for team consistency: mirror old HTML document structure on every page — **fixed header → body (containing all content blocks) → footer** — as the standard top-level grouping regardless of what's inside.

## 09. Design System

The PDF states "codify grid/type/components." The video is the only place that shows an actual finished design-system document's table of contents and the Atomic-Design component taxonomy with a live demo of *why* it's fast.

- **Explicit threshold for when a design system is worth building** (sharpens the PDF's vague claim): needed when you have multiple sub-brands/verticals under one master brand, or multiple people/teams producing many pages/products off one system (Airbnb named as the example). Direct counter-rule: *"not every project needs a design system... if you're just doing a small site with barely any designs on it, you don't need one."*
- **Actual section order of a shipped design system**, usable as a build checklist:
  1. Cover / one-line purpose statement + who it's for (audience: design, engineering, marketing).
  2. Link to the **live, editable Figma file** + a feedback channel + a **named project owner** who maintains the system (not "the team," a specific person/role).
  3. Link back to the design-vision doc — the system explicitly references the vision/strategy rather than restating it.
  4. **Copywriting / tone-of-voice as a first-class section**, stated directly: *"words make up design as well."* Treated as equal-weight to typography/color, not an afterthought.
  5. Typography: downloadable font files; a small, tightly governed set of **base UI typefaces** (2, in this project) vs. a separately-listed, deliberately looser set of **approved display fonts for campaigns** (example given: an ultra-condensed Univers weight used only for one seasonal campaign). Explicit reasoning for the split: *"you always want to give some room for flexibility with the design system — you don't want it so rigid that people feel like they can't add to it and make it better."*
  6. Typographic scale as a **live table** (font size / line height / heading level) with **hover-to-preview** showing the style used in real context — plus a *separate* small-screen (mobile/tablet) type-size table, not just a scaled-down version of the desktop one.
  7. Color: downloadable swatches in multiple formats, **primary palette** (core UI) vs. **secondary palette** (backgrounds/emphasis) kept visually and structurally separate, click-to-copy hex values. Explicit e-commerce-specific color rule: *"use the imagery as the basis for color... the image is the product... we want to kind of be invisible and get out of the way most of the time."* — i.e., for shopping sites, brand color should recede so product photography reads as the primary color signal.
  8. Photography/image library as its own governed, searchable section (downloadable + filterable online) — treated as a design-system asset class on par with color and type, not just "assets somewhere."
  9. **Responsive image rule stated explicitly**: product images must maintain the same aspect ratio from full-size down to thumbnail, so one source image can scale cleanly across contexts instead of needing separate crops per size — framed as a direct collaboration point with engineering, since "the developers are actually a lot closer to the end user... not our flat designs in Figma."
  10. Grid system shown live/responsive across desktop/tablet/mobile, plus a callout that in this system **button color itself is semantic** — e.g. "every time it goes to a codebase, it's this [color] button; every time it's a download, it's the black button" — i.e., color-code button meaning consistently across the whole product, not just per-screen.
  11. Components, organized **Atomic-Design style**: **Atoms** = buttons, icons, form fields, individual type styles, spacing blocks (spacing atoms are grid-unit based — same 12px unit from part 08.1, scaling up from there). **Components** = the bigger reusable blocks made of atoms: navigation, banners, article/news blocks, product blocks, footers.
- **Naming-convention rule, stated directly and generalizably**: pick ONE team-wide term per component and enforce it everywhere, even when synonyms exist — his examples: always say "navigation," never "menu"; always say "banner," never "hero" or "marquee." The specific word doesn't matter; consistent team vocabulary does.
- **Explicit anti-pattern named**: *"you can categorize it by breakpoint types if you wanted to — I would advise against that."* Organize the component library by what a component IS (product, cart, footer, navigation), never by which screen size it happens to appear at.
- **The real payoff of naming discipline, demonstrated live**: with components properly named/tagged, typing "logo" or "tag" into Figma's asset search instantly surfaces the right piece — the entire justification for naming rigor is this search speed, not tidiness for its own sake.
- **Live composition demo proving the speed claim**: built a brand-new page section from scratch in minutes purely by dragging pre-made components out of the assets panel (banner + news block + product block + testimonial block), only detaching one instance to prune it down — explicitly framed as what "hundreds or thousands of pages" of production speed looks like in practice, not a hypothetical.
- **ROI pitch to give stakeholders for buy-in**, stated as the actual talking point to use: a design system is an ongoing maintenance cost, but if built to be flexible/updatable from the start, the speed + consistency payoff at scale offsets that cost — frame it as an efficiency investment, not a one-time deliverable.
