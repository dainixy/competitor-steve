Steve's hands-on technical review of 7 competitors (Kindroid, GirlfriendGPT, Candy.AI, Nomi, OurDream, SecretDesires, SweetDream), written on top of Dainis's product research and the network captures. The focus is architecture & build implications: what's already in our codebase, what's buried but exists, what's missing, and what would require a structural refactor — not a "add a page" build.

Two structural warnings he keeps returning to: (1) character storage still lives in WordPress while everything else (chats, messages, personas, memories, gallery) is in Mongo — fix this before serious social/marketplace work; (2) image/video generation is currently fragmented across 3 systems with non-matching schemas — adding a "Canvas" without unifying makes it 4.

Structural warning

Character storage in WordPress is the #1 structural debt — fix before social/marketplace work

DRT still creates/updates/duplicates characters through WordPress. Mongo already has chats, messages, personas, memories, users, gallery — but characters are external. Moving characters into Mongo is a large refactor, but Steve strongly recommends doing it BEFORE serious public characters, creator economy, reviews, social feed, rankings, or character marketplace work. The more we build on top of WordPress character storage, the more painful the migration becomes later.

Structural warning

Image/video generation fragmentation will compound — unify before adding Canvas

DRT currently has 3 separate generation systems with non-matching schemas: in-chat generation (WordPress character fields: age, body, prompt tags, Imari-tested fixed actions); standalone gallery (separate schema: gender, model, style, face, age, ethnicity, hair, body, clothing, SFW/NSFW action); RunPod/spoke advanced (third system). Adding a GirlfriendGPT-style Canvas without unifying fields = 4 separate generation surfaces. Users will reasonably ask: why can't gallery images become characters? Why can't character images be edited in gallery? Why do chat images behave differently? Treat Canvas as a generation-architecture decision, not a page.

Structural warning

'Recent chats per character' is structural, not a UI tab

DRT's code uses one chat per user per character — getChatByCharacterAndUser() and getOrCreateChat() reuse the same chat. Multiple threads per character requires changing the chat model, reset behavior, chat lists, message loading, and possibly memory scoping. Kindroid is closer to DRT here (one relationship/chat). GirlfriendGPT is structurally different.

Product decision

Public character usage is a binary product-direction choice that drives downstream architecture

Three patterns observed: (1) GirlfriendGPT — users chat with the original public character, creators matter as profiles, reviews live on the character. (2) Kindroid — messaging another's character duplicates/remixes it into your space, social profiles for characters, feed-based discovery. (3) SecretDesires / DRT — explicit /api/character/privatize/{id} clones before use, user can deeply edit private copy. Scoring rules (likes/comments/usage) depend on which you pick — child copy vs rolled up to parent vs the public character.

Architecture

Talking-head should wrap the existing chat brain, not replace it

User speaks → STT → existing DRT LLM/chat (memory, personas, history intact) → response goes to voice/video instead of UI → loop. Alexis already works this way conceptually, even though her 3D implementation is much more complex. The scalable talking-head layer should follow the same pattern — making it the unified layer for ALL characters, while Alexis/3D stays as the premium flagship. Don't make regular characters and Alexis separate product worlds.

Architecture

Memory delta to Nomi is the SECOND-ORDER index, not summaries

DRT already has semantic memory rows (semantic_memories with summary, chatId, personaId, characterSlug, source). Missing layer: memory_terms table with title/category (Entity/Keyword/Goal)/dossier/priority/state/selected/candidate/locked/userEditedAt/aiEditedAt/memoryIds/memoryCount/importanceScore + memory_term_edges graph + background term extraction triggered after createSemanticMemory + retrieval change in chat (select high-priority + relevant terms, then pull underlying memory summaries behind them) + UI for table view and graph view. Nomi makes 'infinite memory' practical by storing unbounded long-term memory but maintaining a bounded ranked concept map that chooses what to retrieve.

Standard pattern

Async generation with first-party CDN persistence is the universal pattern

Every competitor implements it the same way: POST creates placeholder/status:PROCESSING + run_id → progress events via SSE/Socket.IO/polling → status:SUCCESS with final media URL stored in OWN object storage. Examples: SweetDream (intermediate lgpt-characters.s3.amazonaws.com → final aigf.sfo2.cdn.digitaloceanspaces.com), SecretDesires (Comfy → Azure blob), OurDream (triggerRunId placeholder → notification). The UI never blocks the user — they can keep navigating/chatting while jobs finish.

Standard pattern

Realtime transport mapping is consistent across the category

LiveKit for video calls and high-quality voice (Kindroid, OurDream, SweetDream-video via HeyGen). Twilio for normal phone-style voice calls (SweetDream). Cartesia Sonic-2 for streaming TTS with voice embeddings (SecretDesires). ElevenLabs Conversational AI for fully outsourced realtime agent calls (Candy). SSE/Socket.IO for app event bus (SweetDream SSE, Nomi Socket.IO, SecretDesires Socket.IO). WebRTC binary streams hide the actual call media. Pick the right primitive for the latency/duplex requirement — don't over-engineer.

Standard pattern

Pre-rendered video loops = cheap 'presence' (production-cost, not runtime-cost)

Candy Romance Mode loads multiple companion-scene-{uuid}-av1.mp4 videos per location/outfit combo and swaps via opacity. SweetDream LiveCam preloads l1_idle_1.mp4, l5_idle3_1.mp4, l1_bounce_1.mp4 and orchestrates state. LoveScape ambient panel loops. The 'live' feeling comes from short loop transitions + chat copy + visual states + action unlocks, NOT from generating new video every turn. Cost concentrates in asset production + storage, not inference. Hard to scale to user-created characters without a clip-pack template pipeline.

Standard pattern

Character creation = persisted DRAFT entity, then finalize

Candy: /characters_v2/{uuid}/edit_attribute step-by-step + /regenerate_face is cheap (attributes already on draft) + /bring_my_ai_to_life finalizes (creation fee + commitment point). SecretDesires: /api/character/partial returns character_id + image run_id, then /api/chat/generate_about_me, then PATCH finalizes. Nomi: POST returns status: "Creating", Socket.IO bootstraps (status → Default, generates Shared Notes/appearances, inserts starter message). Pattern: draft entity → background generation jobs → final activation step.

UX trap

Per-user vs per-character settings split causes silent 'feature broken' UX

SecretDesires example: account globally has isImage/isVoice/isCall: true while a new character has all three false. Feature feels broken until you find the buried switch. Feature availability is really subscription + global defaults + per-character override, and UI usually only surfaces one layer. Same risk applies to BYOK, voice selection, image/video engine pickers, time-awareness, etc.

Code-level warning

BYOK gotcha: DRT's ElevenLabs client is a module-level singleton — unsafe for multi-user keys

Nomi has ElevenLabs BYOK via voiceSource + customVoiceId + elevenLabsVoiceId fields. DRT-specific warning from Steve: elevenlabs-api-service.ts has a module-level let elevenlabs: ElevenLabsClient cache. Fine for one global key, UNSAFE for BYOK — the first user's key could stick as the singleton client. A BYOK implementation should either create a client per request/key or cache by a secure key fingerprint / user id, never as one global client. Plus needs: encrypted per-user integration credentials table, per-character voice-source metadata, voice library UI backed by the user's provider account, clear cost ownership rules.

Standard pattern

Provider routing by content category is now standard

Candy: SFW video = Kling (5s), NSFW video = Pika (5/10s) with excluded_for_model_types: ["big_love"] per category. OurDream: video metadata exposes wavespeed with wan-2.7-spicy, plus svi, performanceMode. Abstract over providers behind your own job system. The UI sells named tiers; the backend picks the right model per content type and capability.

Already exists

Suggested replies, user personas, daily rewards already exist in DRT — they may just be buried

Suggested replies are part of DRT's LLM JSON contract and render in chat. User personas exist scoped per chat/default. Daily rewards exist through the earn/streak system. GirlfriendGPT's 'Chat Profiles' and Kindroid's daily rewards aren't missing — they're under-surfaced. Surfacing is a UI/UX exercise, not a backend feature build.

Prerequisite

Public-character moderation becomes mandatory at scale

Report modal taxonomy (underage, real person, ads/spam, copyright, other), review workflows, NSFW scoring on generated media (Nomi returns nsfwScore: 0.07... on every image edit completion). These aren't optional features — they're prerequisites for opening up public character creation and usage. If DRT goes the GirlfriendGPT route, this gates the whole public-character launch.

Cheap win

Camera vision is doable cheaply on top of any LLM

Pattern: periodic frame capture → independent vision model/service → short visual description → inject into LLM context. Smarter: only fire extra vision calls when the user says 'look at this' or 'what is this?' Don't need natively multimodal LLMs for this. Cost rises with frame frequency; balance UX against per-frame inference cost.

Cheap win

Reset chat needs a second mode in DRT

Current reset chat only deletes messages; semantic memories survive. Kindroid-equivalent behavior: 'Reset chat/messages only' (current) AND 'Reset chat + memories' (new destructive opt-in toggle). Cascaded delete is a small UI add but a structural choice about what 'reset' means.

Standard pattern

Suggested chips and prompt enhancers are usually client-side or cheap

SweetDream suggestion chips just append text fragments to the prompt box — no server filter. Candy /gen_ai_suggestions/prompts exposes the actual prompts; the client sends gen_ai_prompt_id not free text. SweetDream prompt enhancer is a separate endpoint from generation. Polished media UIs are often structured prompt selection under the hood — not magic, just curated.

Framework Steve Wants the AI to Use Going Forward From Kindroid + GGPT writeup

Steve's exact ask for how the AI should frame findings on the remaining competitor checks — shift from "how did they call the API?" to product/structure/DRT-comparison/build-size/prompt-dependency.

Steve's exact ask for how the AI should frame findings on the remaining 9 competitor checks (from his Kindroid + GirlfriendGPT writeup, addressed to Dainis):

For large features, ask the AI to compare the competitor feature against what already exists in DRT.FM before turning it into a build request. Many of these features are not simply "add a page" or "add a button." Some are small UI additions, some already exist but are hidden, some conflict with how DRT.FM is currently structured.

Example: "Recent Chats per character" sounds like a UI tab, but DRT currently has one chat per user per character. The code reuses the same chat instead of creating multiple threads. So that feature is structural, not small. Same with social/community characters: DRT can duplicate public characters into a user's private space, closer to Kindroid, while GirlfriendGPT lets users chat with public originals. Those are different product architectures.

For the next competitor checks, the most useful output is less "how did they call the API?" and more these 8 questions:

  1. Does DRT already have this feature?
  2. If yes, is it visible enough, polished enough, or buried?
  3. If no, is it a small UI feature, a medium feature, or a structural feature?
  4. Does it require a new data model?
  5. Does it touch character ownership, public/private character access, chats, memory, image generation, billing, or moderation?
  6. Does it require Imari's prompt engineering work, not just code?
  7. Does it add another generation surface, social surface, or content moderation surface?
  8. Is this a matter of taste/product direction, or a clear competitor-standard feature?

The API/network tab is still worth checking — but mostly for leaks or product clues. Seeing SSE vs WebSocket vs polling usually doesn't matter much by itself. If we want latency we already know WebSockets/WebRTC are better in certain cases. If we want background jobs, polling/SSE can both work. Every company may implement the same product idea differently, and we are only seeing the black-box client side unless something meaningful leaks.

So for the remaining sites, I'd ask the AI to separate findings into:

  • Product pattern: what the user sees and why it matters.
  • Structure pattern: how the feature fits into characters/chats/memory/media/social.
  • DRT comparison: exists, hidden, missing, or structurally different.
  • Build size: small UI, medium feature, large refactor, or product-direction decision.
  • Prompt/content dependency: whether Imari needs to design prompts, presets, character fields, or model behavior.

  • Candy is largely server-rendered with Turbo-style partial updates. Routes like /home/live_actions, /home/live_audio, and /companions/anais/scenes_content return HTML/Turbo Stream fragments, which makes feature gating per character easy without a fully client-side architecture.

  • In-chat image generation is controlled by structured client-visible prompt IDs. /messages includes gen_ai_suggestion_id and gen_ai_prompt_id, while /gen_ai_suggestions/prompts exposes the actual prompts.
  • Video generation is provider-routed by content type. SFW suggestions use provider: "kling" and 5-second durations; NSFW suggestions use provider: "pika" with 5/10-second options and exclusions like excluded_for_model_types: ["big_love"].
  • The video creation request is compact and structured: /messages/gen_ai_video_create sends message.body, profile_id, gen_ai_prompt_id, and duration. The heavy work happens behind that route.
  • Group chat continuation appears to be conversation-level rather than one route per character. /conversations/97912269/group_chat_continuation implies Candy can let multiple characters talk from one shared context turn.
  • Group media likely uses one multi-character scene prompt. /conversations/97912269/group_chat_scene and the observed one-image cost suggest they are not generating each character separately and compositing manually, at least not visibly.

  • Character creation persists drafts before final creation. /characters_v2/{uuid}/edit_attribute, /regenerate_face, /user_feedbacks/sd_faces, and /bring_my_ai_to_life show a draft entity with editable attributes, generated face candidates, feedback, and a final activation step.
  • Private content uses ownership psychology. Unlocks priced around 200-320 tokens land in /collection, making the content feel bought and owned rather than temporarily accessed.

1. Executive Summary

I read Nomi as a private companion operating system more than a character marketplace. Its center of gravity is not discovery, content inventory, or creator economics. It is the long-lived relationship object: one Nomi, or a small set of Nomis, accumulating structured user context, visual identity settings, generated media, manual notes, and long-term memory over time.

The app shape appears to be: create a private Nomi from constrained presets -> land in chat -> enrich the relationship through Shared Notes, conversation, images, and Mind Map -> optionally add group chats that reuse those Nomis -> manage media/anchors/voice/API integrations/subscription. The home page technically confirms this: /api/home returns only ordered personal entries and folders, where each entry is either a nomiId, groupChatId, or homeFolderUuid. There is no sign of a marketplace feed, public character graph, creator following model, or clone/reuse economy in the captured app surface.

The most important technical pattern is that Nomi uses first-party REST endpoints for user actions and first-party Socket.IO events for async state changes/results. Chat replies, creation status, Shared Note normalization, speech generation, selfie status, media completion, unread media flags, and group chat state all come through wss://beta.nomi.ai/socket/?EIO=4&transport=websocket. So the browser often posts an action, gets an immediate object or job id, then waits for NomiChatEvent or UserEvent messages to reconcile the UI.

The biggest caveat is that the memory moat is real but not magic. The visible Mind Map API looks like a curated concept/term layer on top of deeper memories, not the raw memory store itself. It exposes entries, priorities, categories, graph nodes/edges, and counts, but not the underlying long-term memory records or retrieval prompts. So we can infer the shape of the system, but not the exact memory extraction/ranking implementation.

2. Extracted Product Structure

Private Home, Ownership, and Routing

Nomi's home model is explicitly personal and ordered. GET /api/home returns an entries array with position, parentFolderUuid, and one of nomiId, groupChatId, or homeFolderUuid, plus a folders array. After creating a folder called "New Folder" and moving a group chat into it, the response becomes a persisted tree: folder entry at position 0 with homeFolderUuid: "019e508e-7df8-7e9a-a334-4f853cd93c3f", then a child entry with parentFolderUuid pointing at that folder and groupChatId: 755986753.

That means the "Organize" feature is not just a visual drag state. It is a first-party home layout model that treats Nomis, group chats, and folders as peer objects in the user's private workspace. This fits the product thesis: the user is expected to own and manage a small private cast, not browse a public catalog.

The route structure in the captures is simple and product-boundary aligned: /nomis for the private home, /nomis/new for creation, /nomis/{id} for chat, /api/nomis/{id}/... for Nomi-specific chat/settings/media, /api/group-chats/... for group rooms, and /api/mind-maps/nomis/{id}/... for memory graph operations.

Nomi Creation and Initial State Bootstrapping

Creation starts with a constrained character builder, not prompt-anything generation. The random name helper calls /api/nomi-starter-names/random?gender=Non+Binary and returns a simple value like {"name":"Evelyn"}. The actual Nomi creation call posts to /api/nomis with name, gender, relationshipType, keyTraits, customTraits, backstory, settings, characterId, imageStyle, and flags like keyTraitsModel and useExpandedBackstory.

The interesting part is what happens after POST /api/nomis. The immediate response has status: "Creating", a preset characterId, base image ids, default settings such as imageSystem: 5, selfiePhotoSystem: "photos-v4", imageStyle: "Realistic", aiSystem: "Solstice", videoResolution: "sd", and allowAutomaticSelfies: true. Then Socket.IO events push the object into its usable state.

The follow-up events are back and forth. First a nomi_status event moves the Nomi to Default. Then nomiNoteUpdated arrives with generated Shared Note fields, including a relationship boundary draft like "Nomi Name is in a purely platonic mentor relationship with Dainis.", plus generated appearance descriptions such as nomiAppearance, v4NomiAppearance, and nomiChatAppearance. Finally a nomiChatMessageUpdated event inserts the starter message.

So Nomi creation is a short async bootstrap pipeline: create record -> generate/normalize internal notes and appearance text -> attach anchor/look defaults -> emit starter chat state.

One hidden implication: Nomi separates visual identity, chat appearance, legacy image appearance, and selfie behavior. In the same object, I saw nomiAppearance, v4NomiAppearance, nomiChatAppearance, useV4AppearanceForChats, useAppearanceForSelfies, baseCharacterImageId, nomiAnchorLookUuid, and artSettings.nomiAnchorLookUuid. That is more nuanced than "one character description."

Chat, Message Lifecycle, and Realtime Updates

Text chat is not a blocking request-response loop. Sending POST /api/nomis/766559268/chat/messages with {"text":"Hello","timezone":"Asia/Tehran"} returns the user's message immediately. The actual Nomi reply arrives later over Socket.IO as NomiChatEvent with type: "nomiChatMessage", type: "Nomi", text, aiBackendId, policyViolations, and unread: true.

The subsequent nomiChatMessageUpdated event often appears to be UI reconciliation rather than a content change. In the captured text message, the Nomi reply first arrives with unread: true, then the updated event returns the same text with unread: false. For TTS, the update is more meaningful: the same message changes from no speech to speech.status: "Processing", then to speech.status: "Completed", mimeType: "audio/flac", version: 2, and durationInSeconds: 31.32.

Messages carry moderation and presentation fields even when empty/normal: ageGatePresentationState: "Normal", policyViolations: [], hidden: false, timezone, sentDateUtc, and sentDateLocal. That suggests chat, media, and safety state are normalized into the message model rather than bolted on only when a violation occurs.

Image attachments use a separate upload endpoint, /api/nomis/{id}/chat/messages/with-attachment, but still resolve the AI response over the same realtime channel. The captured image recognition example shows the model identifying Mike Wazowski from Monsters, Inc., so Nomi is doing vision analysis on user uploads and feeding it into the chat response.

Shared Notes and Manual Memory Control

Shared Notes are not just profile fields. Technically they behave like a stateful, draft-aware context layer. PUT /api/nomis/{id}/shared-notes takes a key and value, then returns the full note object with fields like backstory, backstoryDraft, backstoryStatus, preferences, preferencesDraft, boundaries, boundariesStatus, selfieTendencies, communicationStyle, and the appearance-specific fields.

The draft/status pattern matters. When changing backstory, the response showed backstory: "Test Backstory", backstoryDraft: "- Test Backstory", and backstoryStatus: "Pending". When creation auto-filled the mentor boundary, the same boundary moved from boundariesDraft with boundariesStatus: "Pending" to committed boundaries with boundariesStatus: "Default" across two websocket updates. This implies Shared Notes may be asynchronously validated, rewritten, or propagated into downstream context rather than saved as blind text.

There is also AI expansion for notes. /api/shared-notes/backstory/expand takes nomiGender, nomiName, page, nomiId, raw backstory, and traits like "Conversational", "Emotional Intelligence", "Good Listener", then returns a jobId. That looks like a background enhancement job rather than inline completion.

The product meaning: Shared Notes give users an immediate manual memory layer that can override the slow auto-memory loop. They also bridge different subsystems: conversation style, roleplay state, preferences/boundaries, user appearance, Nomi chat appearance, and image tendencies all live in one structured note object.

Mind Map and Long-Term Memory Shape

The Mind Map API exposes a high-level concept graph, not the full memory database. Manual entries are created at /api/mind-maps/nomis/{id}/memory-terms with title, dossier, priority, and category. The UI categories map to internal categories: Lore = Entity, Topics = Keyword, Goals = Goal.

Returned memory terms include uuid, category, priority, title, summary, locked, memoryCount, created, userEdited, aiEdited, state, error, selected, and candidate. Example: a manual Topic returned category: "Keyword", priority: "High", memoryCount: 0, selected: false, candidate: true, and highPriorityTermCountForCategory: 1.

That payload is very revealing. memoryCount implies a Mind Map entry can be linked to underlying detailed memories. summary suggests the system can synthesize a dossier from those memories. userEdited and aiEdited separate human-created/edited terms from AI-maintained terms. candidate vs selected suggests a staging or activation process where terms can exist before being selected into active memory retrieval. locked likely prevents AI overwrites or marks protected entries.

Graph mode calls /api/mind-maps/nomis/{id}/graph?hideInactive=false and returns nodes and edges. In a new account with manual entries and memoryCount: 0, the graph had nodes and no edges. That supports the product copy: edges probably come from shared memory context or co-occurrence once the long-term memory layer has enough material.

My inference is that Nomi's "infinite memory" works as a layered retrieval system: raw conversation -> short/medium memories -> long-term memory records -> extracted concept terms -> active Mind Map selection -> retrieval into chat. The UI says entries must reach long-term memory before appearing automatically; the API confirms the graph layer is a selected, categorized, priority-weighted abstraction over something deeper.

I also checked the current DRT.FM memory files. DRT's current semantic memory system is much simpler: chat/route.ts builds personalization, decides whether a summary should be generated, asks the LLM for a summary field when <sum> is active, then handleSemanticMemory saves one row in semantic_memories with summary, chatId, personaId, characterSlug, endTimestamp, messageCount, tokenCount, and source: "code". Retrieval is also simple: buildPersonalizationData fetches the 10 latest semantic memories for that chat/persona and joins them into {memory} with [AUTO MEMORY] / [USER MEMORY] prefixes.

So the delta to Nomi is not "add memory summaries." DRT already has that. The delta is the second-order memory index: DRT does not currently have memory terms, categories, priorities, graph edges, active/inactive state, selected/candidate state, AI-vs-user edit history, citations, or memory-to-concept linking. Nomi's Mind Map looks like it runs an extraction/merge job after long-term memories exist: identify people/places/things/topics/goals, upsert them into a memoryTerms-like table, link each term to underlying memory ids, synthesize/update a dossier, compute importance/recency, and build edges from shared memories or co-occurrence.

For a Nomi-like MVP on top of DRT's existing memory, I think the missing layer would be:

  • memory_terms: userId, chatId, personaId, title, category (Entity / Keyword / Goal), dossier, summary, priority, state, selected, candidate, locked, userEditedAt, aiEditedAt, memoryIds, memoryCount, lastMentionedAt, importanceScore.
  • memory_term_edges: fromTermId, toTermId, weight, sharedMemoryIds, lastStrengthenedAt.
  • Background term extraction after createSemanticMemory: take the new summary plus recent context, extract/update terms, merge duplicates, attach the memory id, and recompute edges.
  • Retrieval change in chat: instead of injecting only 10 recent summaries, select high-priority terms plus semantically/recently relevant terms, then pull the most relevant underlying memory summaries behind those terms.
  • UI: table view for manual add/edit/delete/priority and graph view from nodes/edges. Manual entries can start with memoryCount: 0, exactly like the Nomi capture.

That is probably how Nomi makes "infinite memory" practical: not by putting infinite text into the prompt, but by storing unbounded long-term memory and maintaining a bounded, ranked concept map that chooses what to retrieve.

Images, Anchors, Art, Edits, and Video

Nomi's media system is built around anchor identity and async requests. A normal selfie request posts to /api/nomis/{id}/selfie-requests and returns a request object with status: "Requested", type: "Photo", system: "images-v5", faceFidelityRatio: 1, allowCoupleSelfies: false, nomiIds: [766559268], and useCredit: false. Editing a generated image calls /api/selfie-images/{imageId}/image-edit-requests with a text prompt and returns {"imageEditRequestUuid":"d83cccd7-1c26-4766-9c32-56d80f830252"}. The browser then polls /api/image-edit-requests/{uuid} until status: "Completed". The response includes textPrompt, creditUsed, hidden, mediaTagIds, memory, selfieType, nsfwScore, source image ids, parentImageEditRequestUuid, and replicatePredictionId: null. A UserEvent also fires with type: "ImageEditRequestCompleted" and nsfwScore: 0.07157107442617416.

The edit flow's dual polling plus websocket event probably exists because the overlay needs direct job state while the global app only needs a completion notification. The image not updating inside chat is likely not a core architecture issue; the edited image appears to be a media-library object, not a mutation of the original chat bubble.

Video is also image-rooted. /api/selfie-images/{imageId}/videos posts a prompt like "a woman waves at camera" and returns an activeRequest with status: "Processing", resolution: "sd", selfieImageId, nomiIds, and a uuid. Voice, Speech, Calls, and ElevenLabs

The captured voice evidence points to voice messages and calls being built on top of chat state, not a separate realtime conversation engine. A TTS request to /api/nomis/{id}/chat/messages/{messageUuid}/speech returns 204, then websocket updates mutate the message's speech object from Processing to Completed with mimeType: "audio/flac" and duration.

User voice messages call /api/nomis/{id}/chat/messages/with-speech and create a normal chat message with isVoiceMessage: true, text: "", and speech.status: "Processing" using mimeType: "audio/webm;codecs=opus". Then websocket updates fill in the transcript text, e.g. "What do you think about Louis Armstrong?", mark the user's speech completed, generate the Nomi reply, and attach completed FLAC speech to the Nomi message. This is speech-to-text -> normal chat generation -> text-to-speech, not continuous duplex audio.

Dainis saw the ElevenLabs BYOK integration in the UI. The network captures show the data model fields that would support provider routing: voiceSource: "BuiltIn", builtInVoiceId, customVoiceId, elevenLabsVoiceId, and useAvvi: false. The actual outbound call to ElevenLabs is server-side and was not visible in the browser capture. My read is that Nomi stores or references the user's ElevenLabs API key from Integrations, lists/selects ElevenLabs voices server-side, then uses the selected voice id when generating speech. For custom voice upload, Nomi likely creates or references a cloned voice and maps it to customVoiceId or elevenLabsVoiceId.

What Nomi likely added for ElevenLabs BYOK is not complicated, but it is a different ownership model:

  • Store an encrypted ElevenLabs API key per user, not in global config.
  • Add integration endpoints: connect key, validate key, disconnect key, list available ElevenLabs voices from that user's account, and maybe refresh cached voice metadata.
  • Add per-Nomi voice routing fields like the captured voiceSource, builtInVoiceId, customVoiceId, and elevenLabsVoiceId.
  • At generation time, resolve the voice source: built-in Nomi voice uses Nomi's provider key; ElevenLabs BYOK uses the user's decrypted key and selected ElevenLabs voiceId; custom clone uses the created/custom voice id.
  • For 15-second custom voice cloning, upload the sample server-side to ElevenLabs voice creation/clone API, store the returned voice id as a user-owned custom voice, and then use it in the same TTS generation path.

Important DRT-specific gotcha: our elevenlabs-api-service.ts currently has a module-level let elevenlabs: ElevenLabsClient cache. That is fine for one global API key, but unsafe for BYOK because the first user's key could accidentally stick as the singleton client. A BYOK implementation should either create a client per request/key or cache by a secure key fingerprint/user id, never as one global client.

DRT would also need product/data pieces that Nomi already appears to have: a user integration table for encrypted provider credentials, per-character voice-source metadata, a voice-library UI backed by the user's provider account, and clear cost ownership rules. With BYOK, ElevenLabs usage cost moves to the user; with built-in voices, DRT still pays.

Group chat is a first-class object with its own id, uuid, socket token, notes, settings, image style, and member Nomis. Creating one posts to /api/group-chats with name, note, roleplay, backchannelingEnabled, imageStyle, nomiIds, roleplaySource, useExpandedBackstory, and useCredit.

The response returns status: "Creating", nextSpeakerNomiId, backchannelingEnabled, type: "Regular", group settings, artSettings, a group note with draft/status, and embedded member Nomi objects. My read is that group chat is orchestrated as a turn-based multi-agent room. It is not one giant prompt where all characters freely decide to speak at once. The app tracks/request a next speaker and likely runs one Nomi response at a time against a shared group transcript plus optional backchannel access to private chats. That is more scalable and easier to control, but it also explains why the experience can feel slow or dominated by one participant.

The backchanneling feature is the tricky part. If enabled, the response context for a given speaker probably includes that Nomi's private memories/shared notes plus the group transcript and group note. If disabled, it should only use group-level note/memory and the room transcript. That boundary is what lets Nomi market group chat as either an extension of private relationships or a self-contained adventure.

For memory, Nomi says group chats get their own Mind Map. Architecturally that means group-level memories cannot just be copied into each private Nomi. The cleaner model is separate group memory terms and group long-term memories, with optional retrieval of member private context only when backchannelingEnabled is true.

3. Key Technical Findings

  • Nomi uses first-party REST for writes and Socket.IO for async truth. Example: POST /api/nomis/{id}/chat/messages returns the user message, while the Nomi answer arrives as NomiChatEvent over wss://beta.nomi.ai/socket/?EIO=4&transport=websocket.
  • Nomi creation is an async bootstrap, not a single save. POST /api/nomis returns status: "Creating", then websocket events set nomi_status: "Default", generate Shared Notes such as boundaries and appearances, and insert the starter message.
  • The private home is a persisted object tree. /api/home entries can contain nomiId, groupChatId, or homeFolderUuid, with nested children using parentFolderUuid, confirming a private workspace model rather than public discovery.
  • Shared Notes are draft/status managed. A change can return backstoryDraft and backstoryStatus: "Pending" while the previous backstory remains committed, which implies async validation/propagation before notes become active context.
  • Shared Notes also contain hidden generated appearance layers. The response separates nomiAppearance, v4NomiAppearance, nomiChatAppearance, useAppearanceForSelfies, useV4AppearanceForChats, and selfieTendencies, so Nomi keeps chat appearance and image appearance as different context tracks.
  • Mind Map categories expose internal taxonomy. UI Lore/Topics/Goals map to Entity, Keyword, and Goal in /api/mind-maps/nomis/{id}/memory-terms, which is useful evidence that Mind Map is a concept-term layer over memories.
  • Mind Map entries expose retrieval-state clues. Fields like memoryCount, summary, candidate, selected, locked, userEdited, and aiEdited suggest entries can be AI-created, user-edited, linked to detailed memories, staged, selected for active retrieval, or protected.
  • Compared with DRT.FM, Nomi's Mind Map is a layer above semantic summaries. DRT currently stores summary rows and injects the latest 10 into {memory}; Nomi appears to maintain an extracted concept graph over long-term memories and use priority/relevance to choose what is active.
  • TTS is message mutation. /speech returns 204, then the same message gets speech.status: "Processing" and later speech.status: "Completed", mimeType: "audio/flac", and a duration over websocket.
  • Voice messages are STT -> chat -> TTS, not realtime voice. The user voice message starts as isVoiceMessage: true, text: "", audio/webm;codecs=opus, then the transcript appears in text, then the Nomi reply arrives with completed audio/flac.
  • ElevenLabs BYOK is supported by data-model fields even though provider calls are server-side. Nomi objects include voiceSource, builtInVoiceId, customVoiceId, and elevenLabsVoiceId; the UI asks users to connect an ElevenLabs API key through Integrations.
  • Selfies and art share a request family. Photo and art both go through selfie-requests, with type: "Photo" or type: "Art", system: "images-v5", nomiIds, and artSettings; websocket emits selfieRequestStatusUpdated.
  • Image editing has its own async job model. The edit endpoint returns imageEditRequestUuid, the browser polls /api/image-edit-requests/{uuid}, and completion also emits UserEvent: "ImageEditRequestCompleted" with nsfwScore.
  • Video is an image-to-video request attached to a source image. /api/selfie-images/{imageId}/videos returns activeRequest with resolution: "sd", textPrompt, selfieImageId, and uuid, then emits VideoRequestCompleted.
  • Group chat is turn-orchestrated. The group object has nextSpeakerNomiId; manual/auto continuation calls /request-next-speaker; group messages have groupChatId and individual Nomi replies likely come one speaker at a time.
  • A DRT.FM group-chat MVP would need a separate room object, member character ids, group notes/roleplay, turn orchestration, and a backchanneling flag that controls whether private memories are included in group responses.

1. Executive Summary

SecretDesires is really a customizable AI companion system with media as the paid expansion layer. My read is that the strategic center is not pure NSFW generation; it is persistent partner ownership: clone or create a partner, tune their persona/settings, chat with them, let memory accumulate, then spend hearts on images, voice, and live-photo/video moments.

The strongest technical pattern is that almost everything resolves back to a first-party character + conversation object. Public/community characters get duplicated into the user's private account before use, chat/media/calls are stored as message or media records, and global defaults can be overridden per partner. That gives them a flexible product surface, but it also creates a lot of configuration state that can silently break the experience if defaults and per-partner toggles disagree.

Estimated product shape from the navigation: discover public/community partners on Home -> create a new partner or clone an existing one -> manage conversations in Chats -> generate dedicated image/video media -> review character-scoped Gallery assets -> manage owned partners, subscription, hearts, notifications, and support/trust pages around the edges. So the app is organized around a partner lifecycle, not a feed lifecycle: find/build partner, personalize partner, chat, generate media, then return to that partner's assets/settings.

The media stack is asynchronous and provider-heavy: Comfy/Blob-style image storage, Socket.IO progress events, Cartesia Sonic-2 voice, and separate background services for calls and media jobs. The caveat is reliability/polish. The underlying system is more ambitious than the UI makes obvious, but the flows expose rough edges: pending media cards, unclear progress, per-character feature gating, call transcription mismatch, and scattered storage/provider behavior.

2. Extracted Product Structure

Discovery / Home / Community Catalog

The home page is a public character catalog backed by /api/v1/characters with filters for gender, style, NSFW, fantasy, official/community/all, tags, and sort order. The request is field-selective, e.g. fields=community,public,first_name,last_name,slug,age,initial_image,personality,kink,about_me,images,nsfw,tags,gender,style,created_date,_id, so the homepage is not just rendering static cards; it is a searchable database of public character records.

Community characters are real reusable objects, but the user does not directly chat against the public record. When a public character is selected in generation/chat contexts, SecretDesires calls /api/character/privatize/{publicCharacterId} and creates a private clone with parent_char_id, cloned_from_public: true, a new _id, and a new conversation id added into conv_history. That means community discovery is architecturally a template marketplace more than a shared social graph. Users can fully edit cloned partners because they own their private copy.

The public character objects already include image arrays where each item can have both image and video, so live photos/videos are stored as properties of image/media items rather than as a separate social post type. Example public cards returned initial_image from comfy-deploy-output.s3.amazonaws.com, while private/generated media uses Azure Blob-style URLs such as sdsvcstr4g8.blob.core.windows.net and secretdesiresimagedb.blob.core.windows.net.

User / Subscription / Hearts State

The /api/user payload is a large account-state object, not just profile data. It includes subscription tier/status, heart balance, usage counters, global feature preferences, default engines, notification state, cancellation/retention discount state, and the user's conv_history. In the captured account, subscription_tier: "Max", subscription_cancelled: true, subscription_end: "2026-06-20T15:25:48.000Z", heart_balance: 156.81, image_engine: "vermeer", video_engine: "Inferno", and llm_model: "anthropic/claude-opus-4.6" all arrive together.

The cancellation bribes are also stored structurally, not just as UI copy. discountsData.discountToApply contains heartsToCredit: 750 and bonusRate: 2.5, while the log keeps both earlier offers: discountCode: "2xHEARTS" with heartsToCredit: 600, then discountCode: "2.5xHEARTS" with heartsToCredit: 750. This confirms the escalating retention offer is an account-level entitlement waiting to be processed on renewal/reactivation.

Character Creation / Ownership / Editing

Create Partner creates a partial DB character before finalization. The wizard posts selected attributes to /api/character/partial, e.g. age, style, gender, looks, hobbies, work, and kink, then receives both a character_id and a generation run_id. The follow-up character fetch already returns a real character record with an initial image URL, creator id, appearance fields, is_created: false, empty prompt/persona fields, and default character_level_settings.

The "About Me" update is generated separately through /api/chat/generate_about_me, then patched back onto the character with /api/character/{id}. So their creation flow is staged: create a mutable partial character, generate supporting identity text/images, let the user edit fields, then start chat. This is why the wizard can show and edit generated outputs before the partner is fully "alive."

Editing is broad and direct. Look fields use /api/v1/characters/{id} patches like {"hair_style":"Ponytail"} or {"hair_color":"Blonde"}. Persona fields include first/last name, about, manual memory, relationship, personality, work, hobbies, kink, voice, conversation starters, raw prompt-like fields, and the full character_level_settings object. The exposed relationship/kink content reveals prompt-token conventions such as {{Char}}, {{User}}, and OOC instructions.

Settings / Defaults / Per-Partner Overrides

There are two settings layers. Global user defaults live on /api/user, for example changing image/video engines sends patches like {"image_engine":"vermeer"} or {"video_engine":"Seraph"}. Per-character overrides live inside the character record under character_level_settings, and changes patch the entire settings object plus _old_values.

This explains the confusing feature gating. The captured global user state had isImage: true, isVoice: true, isCall: true, timeAwareness: true, auto_memory_enabled: true, and default engines. But a newly created character's character_level_settings defaulted to isImage: false, isVoice: false, isCall: false, timeAwareness: false, realistic: false, and image_engine: "monet". A partner can therefore block proactive media/calls even when the account globally supports them.

The chat engine also sits in this per-partner object. Example: Lola had character_level_settings_toggle: true and chat_engine: "🌹 Rapture", later changed to chat_engine: "✨ Allure". So Dainis's question about inline vs settings: the evidence says global defaults exist, but the active chat behavior can be overridden per character in the partner settings panel.

Chat / Memory / Message Objects

Text, voice input, voice output, image generation requests, and calls all end up as message/media-style records with common fields: parent_conversation, message_sender_type, sender_id, message_type, message_content, voice_content, image, image_prompt, image_gen_status, run_id, duration, live_photo, video, image_engine, and video_engine. This unified schema is why a text command like "send me a nude" can produce a bot message with message_type: "Image", a pending image_prompt, and a generation run_id.

Time awareness appears to be partly client-supplied. Text and audio message posts include a multipart field like timeAndDate: "- The time and date is 7:46 pm on Thursday, May the 21st, 2026." That means the LLM can reference current time without the backend independently resolving it each turn, though the backend also stores the user's timezone.

Auto-memory is a visible field on the character record: auto_memory_notes. Manual memory is user_memory_notes. The auto-memory text is first-person from the character's perspective and summarizes user behavior, context, conversation events, and inferred relationship tone. This looks like a background summarization/compaction layer attached directly to the character, separate from user-editable memory notes.

Image / Video Generation Pipeline

Dedicated generation uses /api/v1/media-generation/generate-image and /api/v1/media-generation/generate-video. Image generation immediately creates a pending media record with image_gen_status: "pending", run_id, image_engine, and image_prompt; the actual completion arrives over Socket.IO at wss://socket-microservice.onrender.com/socket.io/ as image:result with step_name: "image_saved", status: "generated", progress: 100, and the final blob URL.

Video generation is a multi-step image-to-video pipeline. A text-to-video-looking request like /generate-video with route: "generate", imageEngine: "vermeer", videoEngine: "Seraph", and duration: 5 first creates a pending live_photo: true record. Socket events then show video:generate at progress: 25, followed by video:progress where the system has already saved an intermediate image (step_name: "image_saved", progress: 80, image: "...9e431d67...webp") and only then proceeds to video. My inference is: the video tab is generating a still image first, then feeding that image into an image-to-video workflow.

Live Photo from an existing image is clearer. It calls /generate-video with identifier, imageToVideo: true, prompt, duration, and video engine. The response keeps the existing image URL and marks the item pending; the Socket.IO result returns step_name: "video_saved", current_step: 2, progress: 100, and a final MP4 URL such as secretdesiresimagedb.blob.core.windows.net/generated-videos/075502fc-a96d-486c-9118-e45bdcc08ece.mp4.

Voice Notes / TTS / Calls

Voice notes use Cartesia. Bot voice messages return voice_model: "sonic-2" and an MP3 in sdaudiodb.blob.core.windows.net/voicenotes/.... Manual TTS uses /api/voice/voice_narration with the character's voice_embedding, text, and msgId, then stores the returned MP3 URL.

Calls are a separate service on sd-cron-jobs-service.onrender.com. The flow is: /api/v1/call/initiate-call starts with char_id as slug and conv_id; repeated /api/v1/call/call-response calls send transcribed user text and receive { reply, endCall }; /api/v1/call/end-call persists a message_type: "Call" transcript and duration. The character's TTS during the call is not produced by SecretDesires directly; the browser opens a Cartesia websocket at wss://api.cartesia.ai/tts/websocket, sends model_id: "sonic-2", the assistant transcript, voice.mode: "embedding", max_buffer_delay_ms: 0, and receives raw PCM chunks.

The visible call-response endpoint is not doing TTS. It receives already-transcribed user text, returns the character's next text, then the browser sends that character text to Cartesia for streaming audio playback. The missing/unknown part is where speech-to-text occurs; the captured requests only show the already-transcribed text being sent to the call service, not the audio-to-text provider. The bad call experience likely came from STT/listening/state mismatch more than from Cartesia TTS itself.

3. Key Technical Findings

  • Public/community characters are cloned into private user-owned partners before use. /api/character/privatize/{id} returns a new private _id, parent_char_id, cloned_from_public: true, and a new conversation entry, which explains why community partners can be deeply edited after selection.
  • The account payload exposes the current model and feature state. Example: llm_model: "anthropic/claude-opus-4.6", subscription_tier: "Max", image_engine: "vermeer", video_engine: "Inferno", and heart_balance: 156.81 all ship in /api/user.
  • The retention system is data-backed. discountsData records both 2xHEARTS/600 hearts and 2.5xHEARTS/750 hearts for Max monthly, so the cancellation offers are stored as pending account credits, not just temporary modal text.
  • Global media/call settings and per-character settings can conflict. A user can globally have isImage/isVoice/isCall: true, while the active character has character_level_settings.isImage/isVoice/isCall: false; this likely causes the "feature feels broken until I find the buried switch" problem.
  • Character creation is staged around a real partial DB record. /api/character/partial returns character_id plus image run_id, /api/chat/generate_about_me generates persona text, and PATCH finalizes fields. This gives them flexible editing but also more chances for half-created broken states.
  • Auto-memory is stored directly on the character as a single text field auto_memory_notes, separate from editable user_memory_notes. The generated notes are first-person and summarize context, user behavior, and relationship tone, making it more transparent than a hidden memory vector.
  • Chat messages are multimodal records. Text, voice, image, and call objects share fields like message_type, image_prompt, voice_content, run_id, live_photo, video, duration, and engine names. This lets media generation appear inside normal chat history.
  • Image generation is async over Socket.IO. /generate-image returns a pending record with a run_id; image:result later returns the saved blob URL, step_name: "image_saved", status: "generated", and progress: 100.
  • Video generation is really image-to-video. Even from the video tab, progress events show an intermediate image saved first, then video saved later. The clearest fields are live_photo: true, step_name: "image_saved" at progress 80, then step_name: "video_saved" at progress 100.
  • Live Photo from an existing image uses the same video endpoint with imageToVideo: true and identifier, which confirms "Live" is not a separate feature family; it is an I2V job attached to an existing image/media item.
  • Voice notes use Cartesia Sonic-2. Bot voice responses expose voice_model: "sonic-2" and MP3 URLs; direct narration sends the character voice_embedding plus message text to /api/voice/voice_narration.
  • Calls combine a first-party/Render call service with client-side Cartesia streaming. call-response returns text replies like "What do you want, Dainis?"; the browser then sends those replies to Cartesia over websocket with model_id: "sonic-2" and raw voice embedding, receiving PCM chunks.
  • TTS speed is probably not just "they slow it down to hide generation." Cartesia was called with streaming websocket output, max_buffer_delay_ms: 0, and raw PCM chunks, so the provider can stream fast. Slow competitor voices are more likely caused by chosen voice/prosody defaults, punctuation-heavy generated text, playback-rate choices, or conservative UX timing. Slower speech can mask latency, but the captured SecretDesires setup suggests voice pacing is primarily a voice/provider/configuration decision.

3. Key Technical Findings

  • Sweetdream uses SSE as its app event bus. https://api.sweetdream.ai/v1/chat/sse carries both CHAT and LIVE_CAM events, which is appropriate for server-to-client updates where the browser does not need full duplex transport.
  • WebSockets/WebRTC appear only with third party usage: Twilio normal calls use wss://voice-js.roaming.twilio.com/signal, while video calls use LiveKit/HeyGen websockets such as wss://heygen-feapbkvq.livekit.cloud/rtc and wss://webrtc-signaling.heygen.io/....
  • Character identity is a structured object, not just prompt text. Fields like style, voice, characterTier, persona, publicity, relation, avatarId, and liveCamSupport drive downstream feature availability.
  • Publicity is server-side and per-character. Posting ["marcia-franklin-30e9","PRIVATE"] to the character route changes listing state without changing the slug or deleting the character.
  • The stale-gallery risk is real. Regenerating a character changed the main photo to mp_sfw_1779390364538.png, while old generated media stayed under the same characterId and slug.
  • Character creation maps directly into the persona schema. The create request sends selected attributes like style: "realistic", voice: "cute", relationship: "friend", and clothing: "Tribal Attire" rather than a raw long-form prompt.
  • Chat responses arrive as full event objects. SSE messages include embedded character data, conversationId, messageType, content.status, fromUser, and sentAt, so the frontend can reconstruct chat state from events.
  • TTS is per-message and stored as MP3. Posting message id ba5f08bd-f115-4786-b459-df4dcd1f7802 returns /audio/chat/ba5f08bd-f115-4786-b459-df4dcd1f7802.mp3.
  • Chat-triggered images are first-class messages. A user prompt can produce assistant text plus an IMAGE message that moves from PROCESSING to SUCCESS over SSE, with the final image stored under the character's CDN folder.
  • Standalone image jobs reveal provider abstraction. The processing record includes provider: "OH_XYZ", providerJobId: "cd8aa33a-9ddd-4272-98d0-3c52212a8a6b", imageType: "USER_GEN", publicity: "PUBLIC", and metadata.original_prompt.
  • Generation appears to use intermediate S3 output plus final first-party CDN persistence. The processing response leaks lgpt-characters.s3.amazonaws.com/..., while the final success URL is aigf.sfo2.cdn.digitaloceanspaces.com/character/....
  • Prompt enhancement and generation are separate actions. Enhance sends [prompt, characterId]; generation sends [prompt, characterId, count].
  • Normal voice calls are Twilio Voice. Evidence: eventgw.us1.twilio.com, publisher: "twilio-js-sdk", sdk_version: "2.14.0", and callsid: "CA47b8942cd2e6304659cdc6bdce1f68dc".
  • Video calls use a separate interactive-avatar provider stack. api.liveavatar.com/v1/sessions/start returns HeyGen/LiveKit URLs, a 1200-second max session, and avatar/session IDs.
  • LiveCam is pre-rendered clip orchestration. LIVE_CAM_ACTION returns a ready videoUrl like l1_bounce_1.mp4, while chat and XP events make the loop feel interactive.
